# 카누맵 회원·커뮤니티·코스·투어 모집 고도화 계획

상태: 기획안 · 화면 시안 승인 전 구현하지 않음
작성일: 2026-09-26

## 1. 목표

카누맵을 단순 지도에서 다음 흐름이 자연스럽게 이어지는 회원 서비스로 확장한다.

1. 카카오 로그인 후 최소 정보로 회원가입한다.
2. 마이페이지에서 저장한 런칭·랜딩지와 코스, 직접 만든 코스를 구분해 관리한다.
3. 장소·코스의 공식 정보와 회원 대화를 명확한 위계로 읽고 답글을 남긴다.
4. 관리자가 검증한 코스를 시리즈·활동 유형별로 발행하고 회원은 필요한 종류만 지도에서 켜고 끈다.
5. 코스에 연결된 투어 모집에 신청하고, 신청 상태와 운영자 메시지를 한곳에서 확인한다.

지도 탐색은 계속 서비스의 중심으로 두고, 커뮤니티 기능이 지도를 가리거나 복잡하게 만들지 않게 한다.

## 2. 현재 구조와 해결할 문제

| 영역 | 현재 | 문제 |
|---|---|---|
| 회원가입 | 닉네임과 필수 동의 2개 | 가입 후 수정 가능한 프로필과 선택 정보가 없음 |
| 마이페이지 | 내 정보·즐겨찾기·내 코스, 투어 사이트에 활동 기록 | 즐겨찾기 장소와 코스가 한 목록에 섞이고, 저장한 코스와 직접 만든 코스의 의미가 불명확 |
| 코멘트 | `관리자 코멘트` 1개와 사용자 코멘트 평면 목록 | 공식 설명·운영자 답변·회원 대화의 위계가 없고 답글 관계를 표현할 수 없음 |
| 코스 | 정적 관리자 코스와 회원 등록 KV 코스 | 발행 상태·검수·시리즈·복수 활동 태그·노출 순서를 일관되게 관리하기 어려움 |
| 메시지 | 없음 | 모집 결과, 준비 안내, 변경·취소 공지를 개인별로 전달할 수 없음 |
| 투어 모집 | 소양호 전용 신청 페이지 | 일반 코스와 연결되지 않고, 모집 상태·정원·대기·참석 처리·개인 메시지가 없음 |

현재 KV의 한 키 안에 배열 전체를 읽고 다시 쓰는 방식은 평면 코멘트에는 가능하지만, 답글·읽지 않은 메시지·신청 상태처럼 관계와 동시 쓰기가 많은 기능에는 맞지 않는다.

## 3. 제품 정보구조

### 3-1. 회원가입

카카오 인증 뒤 한 화면에서 완료한다.

**필수**

- 닉네임: 2~20자, 중복 검사
- 서비스 이용 동의
- 개인정보 수집·이용 동의

**선택**

- 주 활동지역: 시·도 수준만 저장
- 카누 경험: 처음 / 입문 / 중급 / 장거리 경험
- 보유 카누: 자유 입력 대신 제품·형태 선택과 `기타`
- 자기소개: 최대 100자
- 알림: 운영자 메시지·투어 상태 변경의 앱 내 알림 기본 ON

전화번호·이메일·성별·생년은 일반 회원정보로 수집하지 않는다. 긴급 연락처가 필요한 투어는 해당 신청에서만 받고 행사 종료 30일 뒤 파기한다.

가입 완료 후에는 바로 지도로 이동하고, 선택 정보는 `나중에 입력`할 수 있다. 닉네임 변경은 30일에 1회로 제한해 코멘트 작성자 식별이 지나치게 흔들리지 않게 한다.

### 3-2. 마이페이지

모바일에서는 전체 높이 바텀시트, PC에서는 우측 패널을 기본으로 한다.

1. **홈**
   - 프로필, 가입일, 활동지역·경험
   - 저장 장소·저장 코스·내가 만든 코스·신청 투어 수
   - 읽지 않은 메시지와 모집 상태 변경
2. **보관함**
   - `런칭·랜딩` / `코스` 세그먼트
   - 이름 검색, 지역·카테고리 필터, 지도에서 보기, 저장 해제
3. **내가 만든 코스**
   - 초안 / 공개 / 관리자 추천 상태
   - 지도 보기, 공유, 수정, 삭제
4. **투어**
   - 신청 중 / 참가 확정 / 지난 투어
   - 신청 취소, 준비사항, 운영자 대화
5. **메시지**
   - 운영자 안내와 투어별 대화
   - 읽음 상태와 안 읽은 수
6. **설정**
   - 프로필 수정, 알림 설정, 약관·개인정보 내역, 탈퇴

`저장한 코스`와 `내가 만든 코스`는 반드시 분리한다. 전자는 북마크이고 후자는 소유·편집 가능한 콘텐츠다.

## 4. 장소·코스 상세과 코멘트 위계

### 4-1. 상세 화면 순서

1. 제목, 카테고리, 공식·회원 등록 배지
2. 핵심 정보: 거리, 난이도, 예상시간, 적정 계절·수위, 런칭·랜딩
3. **공식 안내**: 관리자가 편집하는 설명. 코멘트가 아니라 콘텐츠 본문으로 취급
4. 안전·접근·주차·캠핑 등 구조화 정보
5. 별점·저장·공유
6. **이용자 대화**

기존 `관리자 코멘트`는 새 구조에서 `공식 안내`로 이관한다. 관리자가 회원 질문에 답한 것은 공식 안내와 섞지 않고 해당 댓글 아래 `운영자` 배지 답글로 표시한다.

### 4-2. 댓글 구조

- 깊이는 **원댓글 + 답글 1단계**까지만 허용한다.
- 원댓글은 최신순, 각 답글은 오래된 순으로 표시한다.
- 관리자가 상단 고정한 원댓글만 전체 목록 위에 둔다.
- 역할 배지: `운영자`, `코스 작성자`, `회원`.
- 수정된 글은 `수정됨` 표시, 삭제된 원댓글에 답글이 있으면 내용만 `삭제된 댓글`로 남긴다.
- 작성자는 자신의 글을 수정·삭제할 수 있고, 관리자는 숨김·복원·삭제·상단 고정이 가능하다.
- 신고 사유: 개인정보, 광고, 공격적 표현, 잘못된 안전정보, 기타.
- 사진은 댓글당 최대 3장으로 확장하되 R2 이전 뒤 적용한다.

표시 예시:

```text
공식 안내
└─ 운영자가 관리하는 장소·코스 설명

이용자 대화
├─ 회원A · ★★★★☆ · 2시간 전
│  ├─ 운영자 · 답변
│  └─ 회원B · 답글
└─ 회원C · 어제
```

## 5. 관리자 코스 발행과 회원 노출

### 5-1. 코스 생명주기

`초안 → 검토중 → 발행 → 보관` 상태를 사용한다.

- 회원 코스: 생성 즉시 `회원 코스`로 공유할 수 있으나 추천 목록에는 들어가지 않는다.
- 관리자 코스: 관리자가 검증 정보와 카테고리를 입력하고 `발행`해야 추천 목록과 기본 지도 레이어에 나타난다.
- 회원 코스 추천: 관리자가 기존 회원 코스를 복제하지 않고 `추천` 상태와 공식 메타데이터를 붙인다. 원 작성자는 유지한다.
- 경로가 변경되면 버전을 올리고 기존 공유 URL은 최신 버전을 열되 변경 이력을 표시한다.

### 5-2. 분류 체계

`시리즈`와 `활동 유형`을 섞지 않는다.

- **시리즈**: 마이카누 엑스페디션 등 연속 기획물
- **활동 유형**: 초보 추천, 종주, 카누캠핑, 당일 투어
- **보조 태그**: 강 / 호수 / 바다, 편도 / 왕복 / 순환, 난이도, 권장 계절

한 코스는 하나의 대표 시리즈와 여러 활동 유형을 가질 수 있다. 지도에서는 다음 카테고리를 독립적으로 켜고 끈다.

- 마이카누 엑스페디션
- 초보 추천코스
- 종주코스
- 카누캠핑
- 회원 공개코스

여러 카테고리에 속한 코스는 중복으로 그리지 않고, 켜진 카테고리 중 하나라도 포함되면 한 번만 표시한다. 마지막 선택 상태는 회원 설정에 저장한다.

### 5-3. 관리자 발행 화면

- 코스 검색과 초안·검토·발행·보관 필터
- 제목, 요약, 시리즈, 활동 유형, 난이도, 예상시간
- 권장 계절·수위와 수위 관측소 연결
- 런칭·랜딩, 포티지, 캠핑 가능 여부, 주의사항
- 대표 이미지와 지도 미리보기
- 발행 기간, 추천 순서, `신규`·`추천` 배지
- 변경 미리보기 후 발행

회원에게는 지도 레이어뿐 아니라 `추천 코스` 목록을 제공한다. 목록에서 카테고리 필터를 선택하면 지도에도 같은 필터가 적용된다.

## 6. 회원 메시지

### 6-1. 1차 범위

처음부터 자유로운 회원 간 DM을 열지 않는다. 신고·차단·스팸·개인정보 노출을 감당해야 하기 때문이다.

1. 운영자 → 회원 개인 메시지
2. 투어 운영자 ↔ 해당 신청자 대화
3. 투어 운영자의 참가자 전체 공지

회원 간 자유 DM은 차단·신고·운영 인력이 준비된 뒤 별도 단계로 연다.

### 6-2. 전달 방식

- 1차: 카누맵 안 `메시지`함과 우상단 안 읽음 배지
- 2차: 설치형 PWA 웹 푸시를 명시적 동의로 추가
- 카카오 로그인만으로 임의 카카오톡 발송 권한이 생기지는 않으므로 카카오 DM을 기본 전달수단으로 가정하지 않는다.
- 긴급 변경은 앱 내 메시지와 모집 시 별도 동의받은 연락처를 함께 사용한다.

메시지는 제목 없이 짧은 대화형으로 제공하고, 시스템 상태 변경은 `참가 확정`, `대기 전환`, `일정 변경`, `취소` 카드로 구분한다. 회원은 운영자 대화 차단은 할 수 없지만 알림을 끌 수 있고, 탈퇴 회원에게는 새 메시지를 보내지 않는다.

## 7. 투어 참가자 모집

### 7-1. 투어 분류

- 당일 투어
- 카누캠핑
- 종주·원정
- 입문·교육
- 번개·자유모임

분류와 별도로 난이도, 숙박 여부, 장비 제공 여부, 유료·무료, 최소 경험을 둔다.

### 7-2. 모집 정보

- 연결 코스와 지도 미리보기
- 일정, 집결지, 예상 종료, 정원, 신청 마감
- 주최자, 난이도, 예상 거리·시간
- 필수 장비, 제공 장비, 비용, 취소 기준
- 수위·기상 취소 기준과 안전 고지
- 선택형 신청 질문과 행사 전용 긴급 연락처

### 7-3. 신청 상태

`신청 → 승인 / 대기 / 반려 → 참가 / 불참`으로 관리한다.

- 정원 도달 뒤 신청은 자동 대기 처리한다.
- 취소가 생기면 대기 1순위를 자동 승인하지 않고 운영자에게 승인 후보로 알린다.
- 운영자는 개별 승인, 일괄 공지, 신청 마감, 일정 변경, 취소를 수행한다.
- 상태가 바뀌면 메시지함에 시스템 메시지가 생성된다.
- 신청자는 다른 참가자의 이름·연락처를 볼 수 없다.
- 투어 종료 뒤 운영자는 참가 여부를 기록하고, 이벤트 전용 연락처는 30일 뒤 자동 삭제한다.

코스 상세에 모집 중인 투어가 있으면 `이 코스로 예정된 투어` 카드를 보여주고, 지도에는 별도 모집 마커를 늘리지 않는다.

## 8. 저장 구조와 API

### 8-1. 저장소 원칙

- 지도 원천·공개 GeoJSON·정적 코스 경로: 현재 파일·CDN 구조 유지
- 기존 로그인 토큰과 관리자 인증: 현재 Worker 계약 유지
- 회원 프로필의 최소 정본: 기존 KV에서 D1로 점진 이전 가능
- **댓글·답글·코스 발행 메타·메시지·투어 모집은 D1로 신규 구축**
- 사진: 현재 KV 이미지는 호환 조회, 신규 다중 사진은 R2

D1 도입 이유는 검색 속도가 아니라 댓글 부모 관계, 읽음 상태, 신청 상태, 정원, 관리자 필터, 동시 쓰기의 정합성 때문이다.

### 8-2. 핵심 테이블

- `members`, `member_profiles`, `member_preferences`
- `saved_items`
- `course_publications`, `course_series`, `course_categories`, `course_category_links`
- `official_notes`
- `comments`, `comment_reports`, `comment_moderation_log`
- `conversations`, `conversation_members`, `messages`, `message_reads`
- `tour_events`, `tour_applications`, `tour_application_answers`
- `notifications`

모든 외부 응답은 원본 카카오 ID가 아닌 현재 16자리 가명 회원번호를 사용한다. 댓글과 메시지에는 작성 당시 닉네임을 복제하지 않고 회원 참조를 사용하되, 탈퇴 시에는 `탈퇴회원`으로 익명화한다.

### 8-3. API 초안

- `GET/PATCH /me`, `GET/PATCH /me/preferences`
- `GET /me/saved`, `POST/DELETE /me/saved/:target`
- `GET/POST /comments`, `PATCH/DELETE /comments/:id`, `POST /comments/:id/report`
- `GET /course-catalog`, `POST /admin/courses/:id/publish`
- `GET /categories`, `PATCH /me/course-filters`
- `GET/POST /conversations`, `GET/POST /conversations/:id/messages`
- `GET /notifications`, `POST /notifications/read`
- `GET/POST /tour-events`, `POST /tour-events/:id/applications`
- `PATCH /tour-applications/:id/status`

쓰기 API는 현재와 같이 Origin 검사, 활성 회원, 만료 전 서명 토큰을 모두 확인한다. 관리자 작업은 별도 감사 로그를 남긴다.

## 9. 실제 서비스 운영 기준

### 9-1. 용량 목표와 서비스 수준

초기 목표는 `가입 회원 100명 이상`, 설계 여유는 `회원 1,000명·동시 사용자 100명`으로 둔다. 100명은 서버 용량보다 개인정보와 권한 오류가 더 큰 위험이므로 아래 기준을 출시 조건으로 삼는다.

- 공개·회원 API 정상 응답률 99.5% 이상
- 읽기 API p95 500ms 이내, 쓰기 API p95 1초 이내
- 지도 첫 유효 화면 LCP 2.5초 이내를 목표로 측정
- 댓글·신청·메시지 중복 생성 0건: 모든 쓰기에 멱등 키 사용
- 운영자 권한 오남용과 개인정보 조회를 감사 로그로 추적
- 장애 시 지도 읽기 기능은 커뮤니티 쓰기 기능과 독립적으로 계속 제공

출시 전 평상시 20명, 순간 100명 동시 요청과 30분 지속 부하를 도구로 재현한다. 목표를 넘지 못하면 기능을 줄이거나 캐시·인덱스를 보완한 뒤 배포한다.

### 9-2. 인증과 권한

- 현재 카카오 인증과 `active` 회원 검증 원칙은 유지한다.
- 장기적으로 브라우저 `localStorage`의 30일 서명 토큰 대신 짧은 접근 세션과 `HttpOnly·Secure·SameSite` 쿠키 기반 갱신 세션을 사용한다.
- 이를 위해 `api.crowdbase.kr` 같은 동일 사이트 API 도메인 또는 동일 출처 프록시를 먼저 마련한다. 도메인 구성이 해결되기 전에는 DM·투어 연락처 기능을 정식 출시하지 않는다.
- 관리자 기능은 브라우저에 저장한 공용 `ADMIN_KEY`에서 회원별 `admin/moderator` 역할로 전환한다. 중요 작업은 재인증하고 가능하면 패스키 또는 2단계 인증을 추가한다.
- 모든 쓰기에서 로그인 여부뿐 아니라 대상 소유권과 역할을 서버가 다시 검사한다. 클라이언트에서 숨긴 버튼은 권한 통제가 아니다.
- 관리자 코스 발행, 댓글 숨김, 신청 상태 변경, 연락처 조회, 전체 메시지 발송은 작업자·시각·대상·변경 전후 값을 감사 로그에 남긴다.

### 9-3. 웹 보안

- 현재 대형 인라인 스크립트를 버전된 동일 출처 JS·CSS로 분리하고 엄격한 CSP를 적용한다. `unsafe-inline`에 의존하는 이벤트 속성도 단계적으로 제거한다.
- Leaflet 등 외부 의존성은 자체 호스팅하거나 고정 버전과 무결성 검증을 사용한다.
- CSP, HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, 프레임 삽입 차단을 적용한다.
- 비공개 API의 CORS는 `canoe.crowdbase.kr`과 `tour.crowdbase.kr`의 정확한 Origin만 허용하며 `*`를 사용하지 않는다.
- SQL은 D1 바인드 파라미터만 사용하고 댓글·메시지는 HTML을 저장하지 않는다. 링크는 `http/https` 허용 목록을 통과한 것만 렌더링한다.
- 이미지 업로드는 확장자가 아니라 실제 MIME 매직바이트·해상도·용량을 검사하고 서버에서 다시 인코딩해 EXIF 위치정보와 비정상 페이로드를 제거한다.
- 가입·로그인 이상 징후와 공개 폼에는 Cloudflare Turnstile을 선택적으로 사용한다. 정상 회원의 매 댓글마다 퍼즐을 요구하지 않는다.

### 9-4. 요청 제한과 남용 방지

IP 제한과 회원 제한을 함께 사용하고, 여러 Worker 인스턴스에서 일관되게 적용되는 중앙 저장형 제한기를 둔다. 현재 isolate 메모리 Map 제한만으로는 정식 서비스의 최종 방어선으로 사용하지 않는다.

초기 제한값:

| 작업 | 회원 기준 | IP 기준 | 추가 보호 |
|---|---:|---:|---|
| 가입·닉네임 변경 | 시간당 5회 | 시간당 20회 | 중복·금칙어·Turnstile |
| 댓글·답글 | 분당 5회, 일 50회 | 분당 20회 | 동일 내용 반복 차단 |
| 이미지 업로드 | 10분당 5장, 일 30장 | 10분당 20장 | 크기·MIME·재인코딩 |
| 개인 메시지 | 분당 10건, 일 200건 | 분당 40건 | 수신자·대화 권한 검사 |
| 투어 신청·취소 | 시간당 10회 | 시간당 30회 | 멱등 키·상태 전이 검사 |
| 검색·목록 조회 | 분당 60회 | 분당 180회 | 캐시·페이지 상한 |

운영 지표를 보고 값은 조정하되 제한을 제거하지 않는다. 반복 신고 회원은 쓰기 제한 → 일시 정지 → 이용 정지 순으로 제재한다.

### 9-5. 데이터 보호와 개인정보

- 행사 연락처는 일반 회원 테이블과 분리하고 Worker Secret으로 애플리케이션 계층 암호화한다.
- 연락처 복호화는 해당 행사의 승인된 운영자에게만 허용하고 조회 자체를 감사 로그에 남긴다.
- 연락처·신청 답변은 행사 종료 30일 뒤 Cron으로 삭제하며 삭제 결과를 운영 로그에 남긴다.
- 인증 토큰, 연락처, 원본 카카오 식별자, 관리자 키는 URL·분석 이벤트·오류 로그·백업 파일에 기록하지 않는다.
- DM은 기본 1년, 일반 알림은 90일 보관 후 삭제하는 정책을 제안하며 출시 전 약관에 명시한다.
- 탈퇴 시 프로필을 익명화하고 법적·운영상 보존 사유가 없는 개인 메시지와 이벤트 연락처는 삭제한다. 댓글은 대화 맥락 보존 여부를 회원에게 명확히 고지한다.

### 9-6. 성능과 트래픽 관리

- 공개 지도·GeoJSON·코스 경로는 CDN 캐시를 유지해 회원 API 장애와 분리한다.
- 회원·댓글·메시지 코드는 마이페이지나 상세를 열 때 지연 로드해 지도 초기 HTML과 JavaScript를 줄인다.
- 목록 API는 커서 페이지네이션을 사용하고 기본 20건, 최대 50건만 반환한다. `전체 배열 반환` API를 만들지 않는다.
- D1에 `target_type+target_id+created_at`, `conversation_id+created_at`, `member_id+status`, `event_id+status` 복합 인덱스를 둔다.
- 공개 카테고리·발행 코스는 짧은 CDN 캐시와 ETag를 사용하고 개인 보관함·메시지·신청 정보는 `private, no-store`로 응답한다.
- 댓글은 10~30초 캐시가 가능하지만 작성 성공 응답에 최신 항목을 포함해 작성자 화면은 즉시 갱신한다.
- 이미지는 R2 원본과 제한된 썸네일 크기를 분리하고 WebP/AVIF를 제공한다. 목록에서 원본을 내려받지 않는다.
- 메시지함은 20~30초 가벼운 폴링으로 시작한다. 100명 규모에서 상시 WebSocket은 불필요하며 실시간성이 실제로 필요할 때 Durable Objects를 검토한다.
- 참가자 전체 메시지는 요청 안에서 N명에게 직접 쓰지 않고 Queue로 분산 처리해 타임아웃과 중복을 막는다.

### 9-7. 정합성과 장애 복구

- 투어 정원 승인과 대기 전환은 D1 트랜잭션 안에서 현재 정원과 신청 상태를 다시 확인한다.
- 모든 POST에는 클라이언트 생성 `idempotency_key`를 받아 네트워크 재시도에도 한 번만 처리한다.
- DB 스키마 변경은 번호가 붙은 마이그레이션으로 관리하고 운영 적용 전 스테이징에서 롤백을 검증한다.
- 제공자의 자동 복구 기능에만 의존하지 않고 일일 암호화 내보내기를 별도 저장소에 보관하며 월 1회 복구 훈련을 한다.
- 새 기능은 기능 플래그로 회원 일부에 먼저 열고, 오류율이 기준을 넘으면 데이터 손실 없이 읽기 전용 또는 이전 UI로 되돌린다.
- 지도·투어·Worker는 개발/스테이징/운영 환경과 저장소를 분리해 테스트 데이터가 실제 회원에게 노출되지 않게 한다.

### 9-8. 관측과 운영 대응

- API별 요청 수·p50/p95 지연·4xx/5xx·D1 오류·Queue 적체·이미지 용량을 대시보드로 본다.
- 로그인 실패 급증, 관리자 권한 실패, DM 발송 급증, 연락처 대량 조회, 신고 누적은 경보를 보낸다.
- 오류 추적에는 요청 ID와 가명 회원번호만 사용하고 민감 본문은 넣지 않는다.
- 댓글·DM 신고 처리 목표시간과 투어 취소 공지 절차를 운영 문서로 만든다.
- 운영자 부재 시 회원 간 자유 DM과 회원 주최 투어를 자동으로 확대하지 않는다.

### 9-9. 출시 보안 게이트

다음 항목을 모두 통과해야 100명 이상에게 공개한다.

- 권한 우회·타인 자료 조회·ID 순회 접근 테스트
- XSS·CSRF·CORS·파일 업로드·SQL 삽입 테스트
- 탈퇴·차단·행사 종료 후 개인정보 삭제 검증
- 100명 동시 부하와 쓰기 재시도·중복 방지 테스트
- DB 백업 복구와 배포 롤백 훈련
- 관리자 감사 로그와 신고·제재 흐름 확인
- 모바일 저속망에서 지도 초기화와 마이페이지 지연 로딩 확인
- 개인정보 처리방침·이용약관·투어 위험 고지 최신화

## 10. 단계별 구현

### 0단계 — 디자인·데이터 확정

- 회원가입, 마이페이지, 댓글, 추천 코스, 투어 모집 화면 시안 제작
- D1 스키마와 KV 백업·복구 절차 검토
- 기존 장소·코스 안정 ID 및 별칭 계획과 연결

### 1단계 — 회원가입과 마이페이지

- 프로필 선택 항목과 수정 화면
- 보관함의 런칭·랜딩 / 저장 코스 분리
- 내가 만든 코스 분리
- 메시지·투어 탭은 빈 상태 UI까지만 준비

### 2단계 — 댓글 위계 정리

- `관리자 코멘트`를 `공식 안내`로 이전
- D1 댓글과 답글 1단계, 본인 수정·삭제, 관리자 고정·숨김, 신고
- 기존 KV 코멘트 백필 후 일정 기간 이중 읽기, 검증 뒤 KV 쓰기 종료

### 3단계 — 관리자 추천 코스와 카테고리

- 발행 상태와 시리즈·활동 유형
- 관리자 발행 화면
- 추천 코스 목록과 지도 카테고리별 ON/OFF

### 4단계 — 투어 모집과 운영자 메시지

- 투어 생성·신청·승인·대기·취소
- 신청자별 대화와 전체 공지
- 마이페이지 투어·메시지함, 안 읽음 배지
- 행사 전용 개인정보 자동 파기

### 5단계 — 알림·확장

- PWA 웹 푸시
- 참가 후기와 참석 이력
- 운영 여력이 확인된 경우에만 회원 간 DM 검토

각 단계는 `실제 디자인 시안 승인 → 구현 → 데이터 마이그레이션 검증 → 운영 배포` 순서로 진행한다. 한 번에 전부 구현하지 않는다.

## 11. 우선 결정할 항목

1. 프로필 선택 항목을 주 활동지역·경험·보유 카누까지 받을지
2. 회원 공개코스를 기본 지도 카테고리에 포함할지, 목록에서만 찾게 할지
3. 관리자 추천을 원 코스에 붙일지, 검수된 별도 버전을 만들지
4. 투어 운영 권한을 관리자만 가질지, 승인된 회원 주최자에게도 열지
5. 투어 신청 시 전화번호를 모든 행사에서 받을지, 운영자가 필요 항목으로 켜는 방식으로 할지
6. 회원 간 자유 DM은 보류한다는 원칙에 동의하는지

권장 기본값은 `회원 공개코스는 목록에서만`, `추천은 원 코스+검수 버전`, `투어 생성은 관리자부터`, `연락처는 행사별 선택`, `자유 DM 보류`다.
