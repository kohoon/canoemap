# 카누맵 공간객체 통합 계획

- 상태: 설계안 — 구현 전 사용자 컨펌 필요
- 작성일: 2026-09-17
- 범위: 관리자와 사용자가 다루는 장소(점), 지형지물(점), 안전·규제정보(점/면)
- 비범위: 코스·하천·도로 같은 선, 실시간 수위·댐·CCTV 같은 관측 데이터

## 1. 결론

카누맵의 점·면 데이터를 물리적으로 한 파일에 합치지 않고, 하나의 **공간객체(Spatial Object)** 규격과 관리자
관리체계로 통합한다. 화면에서는 사용 목적과 법적 의미를 보존하기 위해 기존 레이어와 세부 유형을 계속 구분한다.

통합 최상위 분류는 다음 두 개다.

1. **장소·지형지물**: 런칭/랜딩, 후보지, 카누명소, 보·징검다리 등 위험지형, 식당/카페, 캠핑사이트
2. **안전·규제정보**: 상수원보호구역, 수상레저금지구역, 물놀이관리지역

상수원보호와 수상레저금지는 면(Polygon/MultiPolygon), 현재 물놀이관리지역 원천은 대표점(Point)이다. 같은
관리 카테고리에 속하더라도 물놀이관리지역을 임의로 면이나 구간으로 추정하지 않는다.

## 2. 현재 구조와 통합 이유

| 대상 | 현재 정본/보정 | 현재 제공 방식 | 주요 문제 |
|---|---|---|---|
| 런칭·랜딩/후보지/명소 | KV `launch_sites_v1` + `placeover`, 레거시 `placecat` | 로그인 `/launch-sites`, 지도 범위 조회 | 지형지물과 CRUD·검색·권한 코드가 분리됨 |
| 지형지물/식당/캠핑 | KV `obstacles` 배열 | 공개 GET + 관리자 전체 POST | 배열 단위 갱신, 장소 기능과 별도 ID·팝업·오프라인 처리 |
| 상수원보호 | `protect_polygons.geojson` 2,156피처 | CDN GeoJSON 지연 로드 | 안정 ID·개별 상태·출처 필드 부족 |
| 수상레저금지 | `wlz.geojson` 246피처 | CDN GeoJSON 지연 로드 | 고시 유효성·정밀도·카누 적용 여부를 공통 규격으로 질의하기 어려움 |
| 물놀이관리 | `waterplay.geojson` 1,336점 + 좌표/요원 보정 파일 | CDN GeoJSON 지연 로드 | 면이 아닌 대표점이며, 위험·관리 상태와 검증일을 다른 안전자료와 함께 관리하기 어려움 |

현재는 장소와 지형지물에서 이름·좌표·메모·공개범위·검색·외부 링크·오프라인 저장을 각각 구현한다. 위치를
옮기면 좌표 slug 기반 코멘트·별점·즐겨찾기도 따로 이관해야 한다. 안전자료는 원천 갱신과 수동 보정의 관계를
각 파일이 서로 다른 방식으로 표현한다. 통합의 목적은 이 공통 작업을 한 번만 구현하고, 원천별 법적 의미는 잃지
않는 것이다.

## 3. 통합 분류 체계

### 3-1. 장소·지형지물 (`place_feature`)

| category | subtype 예시 | 현재 데이터 |
|---|---|---|
| `access` | `launch_landing` | 런칭/랜딩, 런칭/랜딩 후보지 |
| `poi` | `canoe_spot` | 카누명소 |
| `hazard` | `weir`, `stepping_stone`, `low_bridge`, `dragon_teeth`, `shallow`, `rapid`, `wind_zone` | 지형지물 |
| `amenity` | `food_cafe`, `campsite` | 식당/카페, 캠핑사이트 |

후보지는 별도 장소 종류가 아니라 `access/launch_landing`의 `verificationStatus=candidate`로 표현한다. 정식
승격은 `verificationStatus=verified` 전환이다. 캠핑사이트의 초기 관리자 전용 정책은
`visibility=admin`으로 표현한다.

### 3-2. 안전·규제정보 (`safety_regulation`)

| subtype | 현재 도형 | 의미 |
|---|---|---|
| `drinking_water_protection` | Polygon/MultiPolygon | 상수원보호구역 |
| `water_leisure_prohibition` | Polygon | 수상레저 금지구역 |
| `waterplay_management` | Point | 물놀이 관리지역/위험지역 대표점 |

세 유형을 관리자 화면의 `안전·규제정보` 아래에서 함께 검색·필터링한다. 하지만 지도 토글, 색상, 팝업 문구와
행위 판단은 계속 분리한다. 물놀이 위험지역은 수상레저 금지구역이 아니며, 상수원보호 역시 동일한 법적 근거를
갖는 금지구역으로 취급하지 않는다.

## 4. 공통 공간객체 규격

```json
{
  "id": "so_waterplay_1119",
  "geometry": {"type": "Point", "coordinates": [129.0, 37.0]},
  "geometryRole": "representative_point",
  "group": "safety_regulation",
  "category": "waterplay_management",
  "subtype": "risk_area",
  "name": "하거노1교 부근",
  "description": "...",
  "visibility": "public",
  "recordState": "active",
  "verificationStatus": "official_source",
  "designationStatus": "unknown",
  "legalStatus": "not_applicable",
  "validity": {
    "from": null,
    "to": null,
    "recurrence": null,
    "displayText": null
  },
  "source": {
    "authority": "행정안전부",
    "dataset": "생활안전지도 IF_0044",
    "sourceId": "1119",
    "publishedAt": null,
    "checkedAt": "2026-09-10",
    "url": null,
    "accuracy": "official_point"
  },
  "properties": {},
  "revision": 1,
  "createdAt": "...",
  "updatedAt": "..."
}
```

### 필드 원칙

- `id`: 한 번 부여하면 분류·이름·좌표·상태가 바뀌어도 유지한다.
- `geometryRole`: `exact_boundary`, `approximate_boundary`, `representative_point`, `estimated_point`로 도형의
  의미와 정확도를 명시한다.
- `recordState`: `draft`, `active`, `inactive`, `archived`, `deleted` 중 하나다.
- `verificationStatus`: `candidate`, `verified`, `official_source`, `rejected`, `needs_review` 중 하나다.
- `designationStatus`: `current`, `ended`, `unknown`, `not_applicable` 중 하나다. 카탈로그 레코드가
  `active`여도 현재 지정 여부는 별도이며, 최신 정본으로 확인하지 못했으면 `unknown`이다.
- `legalStatus`: `in_force`, `lifted`, `seasonal`, `unknown`, `not_applicable` 중 하나다.
- `visibility`: `public`, `member`, `admin` 중 하나다.
- `validity`: 효력 시작·종료일과 매년 반복 기간을 구조화하되, 원문의 기간 문구도 보존한다.
- `source`: 기관·데이터셋·원천 ID·확인일·정확도를 보존한다. 원천 ID의 존재만으로 현재 지정 상태를
  판정하지 않는다.
- `properties`: 수심, 금지대상, 주차, 카카오 장소 ID처럼 유형별로만 필요한 속성을 저장한다.
- `revision`: 동시 수정 충돌을 막기 위한 낙관적 잠금 값이다.

## 5. 정본과 보정 정책

통합 후에도 공식 원천과 관리자 편집을 한 레코드에 덮어쓰지 않는다.

1. **원천 스냅샷**: 기관에서 수집한 이름·도형·고시·원천 ID를 그대로 보존한다.
2. **관리자 보정**: 좌표, 표시명, 설명, 공개범위, 분류 보정을 별도 override로 저장한다.
3. **유효 객체**: 화면과 검색에는 `원천 + 승인된 override`를 합성한 결과를 제공한다.
4. **감사 이력**: 변경 전후 값, 변경자, 변경일, 근거 URL/문서, 사유를 남긴다.

공식 안전자료는 일반 장소처럼 삭제하지 않는다. 해제 또는 자료 제외가 확인되면 원천 레코드는 유지하면서
`designationStatus=ended`, `legalStatus=lifted` 또는 `recordState=inactive`로 전환한다. 식별자가 남아 있다는
이유로 현재 지정 중이라고 판정하지 않으며, 반대로 최신 목록에서 일시 누락됐다는 이유만으로 자동 해제하지
않는다.

## 6. 안정 ID와 기존 연결 보존

| 기존 대상 | 권장 안정 ID | 비고 |
|---|---|---|
| 카누 장소 ID | `so_place_<기존ID>` | 기존 숫자 ID를 별칭으로 유지 |
| 신규 `u<timestamp>` 장소 | 신규 ULID 기반 `so_<ULID>` | 생성 후 ID 불변 |
| 지형지물 | `so_obstacle_<기존ID>` | 정적 보 `weir:` ID도 별칭 등록 |
| 상수원보호 | `so_protect_<원천ID>` | 다음 원천 갱신에서 VWorld 원천 키 보존이 선행조건 |
| 수상레저금지 | `so_wlz_<원천구분>_<원천ID>` | 해수면/내수면 고시 식별자 분리 |
| 물놀이관리 | `so_waterplay_<objt_id>` | 행안부 `objt_id` 사용 |

현재 상수원보호 결과 파일에는 시·군·구 표시값만 있고 안정 원천 ID가 없다. 도형 해시를 ID로 사용하면 경계가
조금만 갱신돼도 다른 객체가 되므로 금지한다. 원천 캐시를 다시 받을 때 기관 ID를 보존하거나, 최초 마이그레이션
시 별도 ID 레지스트리를 만든 뒤 이름·공간 중첩률로 다음 스냅샷과 대조한다.

기존 공유 URL, 코멘트, 별점, 즐겨찾기는 `spatial_aliases(old_key → object_id)`로 연결한다. 좌표 slug는 이전
호환 키로만 남기고 신규 쓰기는 안정 객체 ID를 사용한다. 위치 이동 때문에 모든 회원 즐겨찾기를 전수 스캔하는
구조도 이 단계에서 제거한다.

## 7. 저장과 제공 구조

### 7-1. 논리적으로 하나, 물리적으로는 목적별 분리

- **관리 정본**: D1의 `spatial_objects`, `spatial_overrides`, `spatial_aliases`, `spatial_revisions`를 권장한다.
- **대형 공개 도형**: 빌드가 D1/원천 파일에서 유형별 GeoJSON을 생성해 GitHub Pages/CDN으로 제공한다.
- **보호 장소**: 회원·관리자 권한이 필요한 점은 Worker가 bbox/검색 제한을 적용해 제공한다.
- **오프라인 팩**: 공통 객체 규격으로 직렬화하되 공개범위와 현재 사용자 권한을 다시 검사한다.

대형 면까지 매번 Worker에서 내려주면 현재의 CDN·줌게이트 장점이 사라진다. 따라서 하나의 관리 모델을 쓰더라도
공개 전달 파일은 `safety-protect.geojson`, `safety-wlz.geojson`, `safety-waterplay.geojson`처럼 분리한다.

### 7-2. API 호환

- 기존 `/launch-sites`, `/obstacles`, 세 GeoJSON URL은 마이그레이션 기간에 유지한다.
- Worker 내부에 공통 저장 계층을 만든 뒤 기존 응답 형식으로 변환한다.
- 관리자용 `/spatial-objects-admin`을 추가해 공통 검색·상세·수정·이력 기능을 제공한다.
- 일반 사용자 응답에서는 후보지와 캠핑사이트 등 비공개 객체를 서버에서 먼저 제거한다. 클라이언트 필터는
  2차 방어로만 사용한다.
- KV에서 D1로 옮겨도 공개 URL과 기존 JSON 계약은 최종 전환 확인 전까지 바꾸지 않는다.

## 8. 관리자 화면 계획

실제 UI는 별도 시안을 보여주고 컨펌받은 뒤 구현한다.

- 진입점: 관리자 메뉴의 `공간객체 관리`
- 상단 필터: `장소·지형지물 / 안전·규제정보`, 세부 유형, 공개범위, 현재 상태, 검토 필요, 원천기관
- 목록: 이름, 유형, 현재 상태, 도형 종류, 공개범위, 최근 검증일, 수정일
- 지도: 선택 객체 강조, 점 이동 또는 면 경계 비교
- 상세 편집: 공통 필드 + 유형별 필드만 표시
- 공식 안전자료: 직접 덮어쓰기 대신 `보정 제안`으로 저장하며 근거와 사유 필수
- 일괄 갱신: 추가·변경·누락 건수와 지도 diff를 먼저 보여주고 승인 후 반영
- 충돌 처리: 열어본 `revision`과 저장 시 revision이 다르면 덮어쓰지 않고 최신값 비교

일반 사용자의 지도 레이어 UI는 1차 통합에서 바꾸지 않는다. 관리 데이터가 통합됐다는 이유로 서로 다른 안전
의미의 토글을 하나로 합치지 않는다.

## 9. 단계별 이행 계획

### 0단계 — 기준선과 백업

- KV의 `launch_sites_v1`, `launch_source_v1`, `placeover`, `placecat`, `places`, `obstacles`를 읽기 전용 백업한다.
- 세 안전 GeoJSON과 보정 파일의 SHA-256, 피처 수, 도형 종류, 속성 목록을 기록한다.
- 배포 시점의 장소·지형지물 수와 공개/관리자 노출 수를 역할별로 기록한다.
- 되돌리기 기준과 백업 복원 명령을 실제 비밀값 없이 문서화한다.

완료 조건: 백업 재읽기 성공, 현재 지도와 객체 수 기준선 일치.

### 1단계 — 공통 규격과 ID 레지스트리

- 공통 스키마와 카테고리 레지스트리를 코드로 정의한다.
- 모든 기존 객체를 공통 규격으로 변환하는 읽기 전용 어댑터를 만든다.
- 상수원보호 원천 ID 확보 방식을 확정한다.
- 기존 ID와 좌표 slug를 `spatial_aliases`로 연결한다.

완료 조건: 기존 자료의 100%가 누락 없이 변환되고, 변환 후에도 기존 화면 출력은 변하지 않음.

### 2단계 — 이중 읽기 비교

- 운영 화면은 계속 기존 경로를 사용하고, 테스트에서만 통합 읽기 결과를 함께 생성한다.
- 객체 수, ID, 이름, 좌표/도형, 공개범위, 상태를 자동 비교한다.
- 면 데이터는 면적·바운딩박스·유효성·MultiPolygon 파트 수를 비교한다.

완료 조건: 의도적으로 승인한 차이 외 비교 불일치 0건.

### 3단계 — 장소·지형지물 쓰기 통합

- 신규/수정/이동/분류/숨김을 공통 객체 쓰기로 전환한다.
- 후보지 승격과 캠핑사이트 관리자 전용 정책을 공통 상태/공개범위 필드로 처리한다.
- 코멘트·별점·즐겨찾기의 신규 키를 안정 객체 ID로 전환하고 별칭으로 과거 자료를 읽는다.
- 기존 `/placeover`와 `/obstacle`은 호환 어댑터로 남긴다.

완료 조건: 저장 후 재조회·새로고침·재로그인 뒤에도 분류, 위치, 공개범위가 유지되고 기존 공유 URL이 열림.

### 4단계 — 안전·규제정보 카탈로그 통합

- 세 원천을 공통 메타데이터로 정규화하고 원천/보정/유효 결과를 분리한다.
- 상수원보호와 수상레저금지는 안정 ID, 현재 효력, 검증일, 정확도를 보강한다.
- 물놀이관리지역은 `representative_point`를 유지하고 공식 면 자료가 생길 때만 도형을 교체한다.
- 유형별 GeoJSON을 새 공통 빌드에서 다시 생성하되 URL과 렌더 스타일은 유지한다.

완료 조건: 2,156/246/1,336 기준 피처가 승인 없는 소실 없이 유지되고 지도 도형 비교가 통과함.

### 5단계 — 통합 관리자 화면

- 목록·필터·상세·이력·지도 diff 시안을 먼저 제시한다.
- 사용자 컨펌 후 관리자 전용 화면만 구현한다.
- 일반 사용자용 레이어/범례 변경은 별도 시안과 별도 승인 대상으로 둔다.

완료 조건: 관리자 역할에서만 노출되고, 각 유형의 저장 결과가 재조회 후 유지됨.

### 6단계 — 전환과 관찰

- 통합 정본을 주 읽기 경로로 전환하고 기존 경로 결과와 일정 기간 계속 비교한다.
- 오류율, 누락 객체, 권한 누출, 저장 충돌, GeoJSON 용량과 로딩 시간을 기록한다.
- 문제가 없을 때만 레거시 쓰기를 중단한다. 레거시 데이터 삭제는 별도 승인 없이 하지 않는다.

완료 조건: 역할별·온라인/오프라인·공유 URL 회귀가 모두 통과하고 관찰 기간 중 치명 불일치 0건.

## 10. 필수 검증 항목

### 권한과 상태

- 일반 사용자에게 후보지·캠핑사이트가 API, 지도, 검색, 오프라인 팩에서 노출되지 않는다.
- 관리자 해제 직후 관리자 전용 객체가 메모리와 지도에서 제거된다.
- ID가 존재하지만 `designationStatus=ended`, `inactive`, `archived`, `lifted`, 유효기간 종료인 객체가 현재
  객체로 노출되지 않는 음성 회귀 테스트를 모든 그룹에 둔다.
- 최신 공식 스냅샷에서 활성으로 확인되지 않은 객체를 단순 ID 존재만으로 활성 처리하지 않는다.

### 데이터 보존

- 기존 공유 URL, 코멘트, 별점, 즐겨찾기가 같은 객체로 연결된다.
- 장소 위치 이동 뒤에도 안정 ID가 바뀌지 않는다.
- 후보지 승격과 유형 변경을 저장한 뒤 새로고침·재로그인·다른 기기 조회에서 유지된다.
- 공식 원천 재수집 뒤 승인된 관리자 보정이 사라지지 않고, 원천과 충돌하면 자동 적용 대신 검토 대상으로 표시된다.

### 도형과 성능

- 상수원보호 면적·MultiPolygon 파트·수상레저금지 경계가 이전 배포와 허용 오차 내에서 일치한다.
- 물놀이관리지역은 계속 점으로 표시되며 임의 면이 생성되지 않는다.
- 줌 11 지연 로드, 캐시버스팅, 모바일 렌더 성능, 서비스워커와 오프라인 팩이 유지된다.
- 공개 GeoJSON에 관리자 메모·비공개 근거·비공개 객체가 섞이지 않는다.

## 11. 롤백 계획

- 각 단계는 기능 플래그로 기존 읽기/쓰기로 즉시 복귀할 수 있어야 한다.
- 마이그레이션 전 KV 백업과 기존 GeoJSON은 관찰 기간 동안 변경 불가 스냅샷으로 보관한다.
- 이중 쓰기 중 한쪽이 실패하면 성공으로 응답하지 않고 재시도 가능한 오류로 기록한다.
- 롤백 시 신규 통합 ID로 생성된 코멘트·즐겨찾기가 사라지지 않도록 별칭 역매핑을 유지한다.
- 레거시 키와 파일 삭제는 통합 완료와 별개의 파괴적 작업으로 취급하고 다시 승인을 받는다.

## 12. 구현 전 승인 항목

1. 최상위 두 분류(`장소·지형지물`, `안전·규제정보`)와 세부 유형표
2. 물놀이관리지역을 `안전·규제정보`에 포함하되 대표점으로 유지하는 원칙
3. 공식 안전자료를 직접 수정하지 않고 원천+보정으로 관리하는 원칙
4. D1을 통합 관리 정본으로 사용하고 대형 공개 도형은 CDN GeoJSON으로 제공하는 하이브리드 구조
5. 관리자 화면 시안과 단계별 전환 순서

이 다섯 항목이 승인되기 전에는 데이터 이전이나 관리자 화면 변경을 시작하지 않는다.
